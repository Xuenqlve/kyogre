# Kyogre Project Rules

## 项目上下文

- 项目名称：Kyogre
- 项目类型：Go CLI / 多数据库压力测试工具
- 当前阶段：Alpha，核心架构已搭建，主流程仍有缺口
- 主要技术栈：Go 1.24、插件/工厂模式、YAML/TOML 配置、MySQL 为当前主落地数据库
- 规范来源：用户需求 + 当前仓库轻量阅读结果

## 项目现状快照

### 已确认信息

- 入口文件为 `cmd/main.go`
- 应用编排在 `internal/app/`
- 配置系统在 `internal/config/` 与 `pkg/config/`
- 数据源、生成器、元数据、压测、场景等能力采用插件化组织
- 可复用实现主要位于 `pkg/`
- 测试主要位于 `test/`
- 当前已有 `README.md`、`CLAUDE.md`、`AGENTS.md` 可作为仓库说明输入

### 基于轻量阅读的推断

- 关键主流程是：配置加载 -> Server 初始化 -> DataSource 配置 -> Metadata 初始化 -> Generator / IQuery / Scenario / Pressure 配置 -> Pipeline 执行
- 当前项目优先保障 MySQL 主链路，其它数据库支持仍偏框架化
- 该项目不适合在单次任务中做大规模架构重排，应采用渐进式收敛

### 待补充信息

- 生产级运行方式与发布流程
- 配置样例与环境约束的统一位置
- 非 MySQL 数据库的实现完成度基线

## 仓库内 Skill 使用约束

- 该 skill 面向当前仓库内的后续 AI 开发任务，不面向通用 Go 项目复用。
- 使用该 skill 时，必须先阅读与任务直接相关的仓库文件，而不是只依赖本 skill 文字描述。
- 若项目现状与本 skill 不一致，应优先以当前仓库代码和文档为准，并在输出中说明差异。
- 若任务涉及本 skill 未覆盖的新模块，应在实现后补充本 skill，而不是长期依赖口头约定。

## 项目目标与主流程约束

- AI 必须先判断任务是否服务于“压测主流程”或其直接支撑能力。
- 涉及主流程的改动，必须优先沿现有链路扩展，不得跳过既有编排层直接拼接调用。
- 若任务涉及 `Server.Run()`、pipeline 生命周期、metadata 初始化、消息流转或 scenario/pressure 协同，必须先说明影响链路。
- 对 Redis、MongoDB、ClickHouse、Kafka 的扩展，必须复用当前插件注册模式，不得新增旁路接入方式。

## AI 工作边界

- 必须优先复用现有工厂注册、manager、plugin 接口和目录边界。
- 可以执行：缺陷修复、主流程补齐、测试补充、小步重构、文档与配置示例补充。
- 应谨慎执行：跨目录重命名、公共接口调整、共享模型修改、并发模型调整。
- 不得执行：无理由重塑架构、引入与任务无关的新分层、用临时硬编码绕过配置/插件机制。

## 目录与模块组织约束

- `cmd/` 只放入口与启动逻辑，不放业务实现。
- `internal/` 用于应用编排、manager、接口组织、内部生命周期控制。
- `pkg/` 用于具体实现、可复用能力、各数据库或引擎落地代码。
- `test/` 用于集成式、流程式或模块级验证，不得把复杂测试逻辑散落回业务目录。
- 新增文件必须优先落入已有职责目录；如需新目录，必须先说明它不能归入现有目录的原因。

## 模块编写约束

- 新增模块必须遵循现有命名风格，如 `Manager`、`Generator`、`Pressure`、`Scenario`、`Metadata`。
- 错误处理必须显式返回，优先保持现有错误包装风格。
- 并发、队列、调度相关实现必须考虑 cancel、stop、close、wait 的生命周期一致性。
- 配置读取必须走现有配置入口，不得绕过 `internal/config` 直接散读文件。
- 若修改公共接口，必须同步检查其 manager、实现层与测试入口的影响。

## 数据流、依赖与边界约束

- 依赖方向必须保持为：入口/编排层 -> 插件接口层 -> 具体实现层。
- 不得让 `pkg/` 反向依赖 `internal/app` 之类的上层编排逻辑。
- 对共享数据结构、消息结构、配置结构的改动，必须评估生成器、场景、pressure、metadata、测试五类影响面。
- 引入新第三方依赖前，必须说明必要性，优先避免为了局部问题扩大基础依赖面。

## 测试策略与补测规则

- 修复缺陷时必须优先补回归测试。
- 扩展主流程、配置解析、元数据构建、生成器、pressure 执行逻辑时，应至少补对应模块测试。
- 并发、worker、queue、scheduler 相关改动应优先跑 `go test -race ./...`。
- 迭代阶段可先跑目标测试，再补跑 `go test ./...`；结束前必须说明是否完成全量验证。
- 若因环境依赖无法跑测试，必须明确缺失环境、未验证范围和风险。

## 变更原则

- 功能开发：优先顺着现有主流程补齐，不做无关重构。
- 缺陷修复：先确认根因，再最小改动修复，并补回归测试。
- 重构：仅在模块边界清晰、收益明确时进行，不得把大重构和功能扩展混在一个步骤里。
- 配置或脚本变更：必须评估对本地运行、测试、后续 CI 的兼容性。
- 文档变更：涉及命令、目录、配置样例时，必须与实际代码状态一致，不得保留失效说明。

## 禁止事项

- 禁止脱离插件化架构另起一套接入路径。
- 禁止把临时调试代码、硬编码库表名、固定连接信息直接并入正式实现。
- 禁止无说明地修改公共接口签名。
- 禁止跳过关键主链路测试判断。
- 禁止把用户已有未提交改动混入当前任务的实现范围。

## Todo List 管理规则

- Todo 必须按“主流程 / 模块 / 测试 / 文档与配置”组织，而不是只按时间顺序堆积。
- 每个任务必须包含：`id`、`title`、`type`、`priority`、`status`；必要时补 `depends_on`、`blocked_by`、`next_action`。
- 任务类型统一使用：`feature`、`bugfix`、`refactor`、`test`、`docs`、`chore`。
- 状态统一使用：`todo`、`in_progress`、`blocked`、`review`、`done`。
- 优先级统一使用：`P0`（阻塞主流程/关键缺陷）、`P1`（重要功能/必要补测/关键重构）、`P2`（增强项/文档/清理）。
- 拆解任务时必须先按主流程分段，再落到模块，例如：
  - `pipeline lifecycle`
  - `metadata initialization`
  - `generator / scenario integration`
  - `pressure execution`
  - `tests and fixtures`
- AI 完成任务后，必须同步记录：完成内容、是否补测、残留风险、下一步建议。
- 已完成任务不得直接删除；应保留以便追踪项目演进。
- 若任务因信息不足或超出边界无法推进，必须标记 `blocked`，并写明阻塞原因和下一动作。
